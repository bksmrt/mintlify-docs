Proof uses multiple LLM providers for extraction, classification, narrative assistance, and chat advisors. Requests are routed through a tiered registry with automatic fallback, and every call is counted for cost and rate-limit tracking. This page explains the provider setup, model management, rate limits, and the RAG retrieval stack.

## Providers

Proof supports three providers. A valid key for at least one must be present at server start.

| Provider | Environment variable(s) |
| --- | --- |
| OpenAI | `OPENAI_API_KEY`, or `AI_INTEGRATIONS_OPENAI_API_KEY` (plus optional `AI_INTEGRATIONS_OPENAI_BASE_URL`) |
| Anthropic | `ANTHROPIC_API_KEY`, or `AI_INTEGRATIONS_ANTHROPIC_API_KEY` |
| Google (Gemini) | `GEMINI_API_KEY`, or `AI_INTEGRATIONS_GEMINI_API_KEY` |

Embeddings run on OpenAI only, so document chunking and retrieval need an OpenAI key even when another provider handles generation. The embedding model defaults to `text-embedding-3-small` (override with `AI_ROUTER_EMBEDDING_MODEL`).

If both an integration key and a plain key are set, the router falls back from the integration client to the plain key on a 401. An integration variable that is set but empty is ignored, so it never hides a plain key. Use `GET /api/setup/ai-status` to verify that at least one provider is configured. The endpoint returns booleans only, with no secrets.

## Model management and routing

### Registry tiers

`server/modules/ai-routing/model-registry.ts` defines three capability tiers per provider:

- `frontier`: highest-capability model for deep reasoning and hardest tasks
- `balanced`: default workhorse for extraction, classification, and JSON tasks
- `fast`: cheapest, lowest-latency tier for rerankers and high-volume passes

Concrete defaults are pinned in the registry. Rotating a model is a one-line change in `model-registry.ts`, or a no-code change via environment variable.

### Routing order

Claude is the primary provider. Each task type leads with the Claude tier judged best for it (`CLAUDE_TIER_BY_TASK` in `router.ts`):

- `fast` (Haiku) for light classification, extraction, and reranking
- `balanced` (Sonnet) for drafting, synthesis, reports, and the advisor chats
- `frontier` (Opus) for strategic plan extraction and approval policy generation

If that step fails, the chain climbs Claude's tiers (`fast` to `balanced` to `frontier`; `frontier` falls back to `balanced`). The OpenAI and Gemini steps from the task's original chain come last. The router reaches them only when every Claude step fails or no Anthropic key is set. A per-task `AI_ROUTER_*_ANTHROPIC_MODEL` override still becomes the first Claude step.

### Tenant scope and provider lists

Every routed call must name the college or firm whose data it holds, or declare a public scope (`publicAIScope`) when it holds none. The router refuses a call that names neither before any provider is asked.

A college can limit which providers its data may reach. The list lives in `institutional_profiles.ai_providers`: null allows every provider (the default) and an empty list allows none. The router removes disallowed steps before the first call. If no allowed provider is left to answer, the call fails with a `ProviderNotAllowedError`.

### Resolution precedence

`modelFor(provider, tier, legacyEnvVar?)` resolves a concrete model ID with this precedence:

1. `legacyEnvVar`: per-task override (for example, `AI_ROUTER_DOC_CHUNK_ANTHROPIC_MODEL`)
2. `AI_MODEL_<PROVIDER>_<TIER>`: registry-level environment override
3. Pinned registry default

### Reasoning effort

OpenAI's GPT-5 family defaults to `medium` reasoning effort, which is too slow for large extraction chunks. The router pins `reasoning_effort` to `low` by default. Override with `AI_ROUTER_OPENAI_REASONING_EFFORT` (values: `minimal`, `low`, `medium`, `high`; empty string to omit the field).

Claude calls send an effort level per model, defined in `server/modules/ai-routing/claude-effort.ts`. Tasks that lead with the `fast` tier run at `low`. Every other task asks for its model's starting level.

### Task types

The router accepts a `taskType` label for every request. Examples include:

- `document_chunk_extraction`
- `policy_summarization`
- `narrative_rewrite`
- `portfolio_query`
- `student_advisor_assistant`
- `workload_advisor_assistant`
- `report_question` and `report_summary`

Task types are used for usage attribution and cost rollup.

## Rate limiting

Interactive AI endpoints (advisor chats, portfolio query) are rate-limited per authenticated user. `server/aiRateLimit.ts` uses `express-rate-limit` with a user-id key generator so one user cannot consume another's budget.

```ts
export const interactiveAiLimiter = buildInteractiveAiLimiter(
  Number(process.env.AI_INTERACTIVE_RATE_LIMIT ?? 30),
);
```

The default is 30 requests per 60-second window. Unauthenticated requests fall back to an IPv6-safe IP key generator, though the downstream `isAuthenticated` gate rejects them anyway.

## Usage tracking and rollups

### Per-call recording

Every routed call records a row in `ai_usage` with tenant, feature, task type, model, tokens, and estimated cost. The `usage-recorder.ts` module handles this automatically inside the router.

### Nightly rollup

`server/aiUsageRollup.ts` runs a daily job that:

1. Aggregates raw `ai_usage` rows within the retention window into `ai_usage_daily` (one row per day, tenant, feature, task, and model)
2. Deletes raw rows older than the retention cutoff

The rollup is idempotent: it recomputes the whole window each run. The retention window is configured by `AI_USAGE_RETENTION_DAYS` (default 90). Rollup rows for days that age out of the window are frozen and kept indefinitely.

## RAG and retrieval

### Hybrid retrieval

`server/modules/evidence-matching/hybrid-retriever.ts` combines:

- **BM25** for keyword and citation matching (for example, "Standard 8.2.a")
- **Vector similarity** for semantic relevance
- **Optional LLM reranking** for a second-stage relevance score

The default configuration uses `bm25Weight: 0.4` and `vectorWeight: 0.6` with reranking on by default. Disable reranking fleet-wide without a redeploy via `AI_ROUTER_RERANK_ENABLED=false`. A reranker error or timeout falls back to the pure hybrid order.

### Narrative RAG adapter

`server/modules/rag/retriever.ts` is a thin adapter that runs the hybrid engine in vector-only mode (`bm25Weight: 0`, `vectorWeight: 1`, `rerank: false`) with section-type weighting enabled. It surfaces top document-chunk matches for narrative annotation generation. Matches with no semantic signal are filtered out so zero-scored lexical filler is not returned.

### Evidence matching

The same hybrid engine powers evidence matching for compliance gaps. It produces a `confidence` score (0-100), a `confidenceBand` (`complete`, `partial`, `weak`, `missing`), and a rationale explaining why the chunk matched.

## Chunking and indexing

Document imports split files into chunks. Each chunk is embedded and stored in `document_chunks`. The platform supports both a legacy JSONB `embedding` column and the pgvector `embedding_vector` column. The retriever tries pgvector first and falls back to JSONB if pgvector is unavailable.

When backfilling embeddings, run `npm run backfill:embeddings`. The streaming import path processes chunks in adaptive concurrent batches and tolerates partial failures: a chunk that fails is retried once sequentially after the burst, and the job completes unless more than half the sections are still missing.

## Diagnostics

If document processing fails:

1. Check `GET /api/setup/ai-status` to confirm at least one provider is configured.
2. Look for `401` errors during chunking, which indicate an invalid or expired credential.
3. Check server logs for `[AI Router] attempt_failure` lines, which print provider, model, path, and error for each failed hop.
4. Verify the model registry default is current: deprecated snapshots return `model_not_found`.
