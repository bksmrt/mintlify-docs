The platform keeps one catalog of agency standards. A pipeline fetches each agency's published source, checks it, compares it with the catalog, and stages the differences for an operator to approve. Approved changes are then delivered to every college that holds the agency, as the college's own copy. Every pass, whatever started it, is a row in one run ledger.

## The run ledger

`pipeline_runs` holds one row per run of a job. `pipeline_run_steps` holds its steps (one per source, or one per college for a delivery).

| Job (`PIPELINE_JOBS`) | Shown as | What it is |
| --- | --- | --- |
| `source_sweep` | Source sweep | The nightly check of every monitored source |
| `prove_agency` | Sync | An operator's Sync of one agency |
| `ingestion` | Fetch standards | The older fetch-and-extract path, joined to the ledger |
| `delivery` | Delivery | A sync of approved changes to colleges |
| `source_repair` | Source repair | The keeper's proposal for one broken source |
| `requirement_checks` | Requirement checks | The nightly list of catalog requirements due for a person's check |

A run records its trigger (`schedule`, `boot`, `catch-up`, `operator`, `approval`, `sync`, `retry`, `keeper`, `college`, `confirmed`), its status (`queued`, `running`, `completed`, `failed`, `interrupted`, `stopped`), its per-stage counts, the app revision and instance that ran it, and a heartbeat. A run whose heartbeat goes silent is closed `interrupted`; a run whose work fails is `failed`.

### Sync stages

A Sync walks one agency through `fetch → gate → read → compare → stage`, then a `deliver` stage that sends only what an operator already approved and nothing has delivered yet. Approval and delivery stay separate acts.

- **Gate.** `shared/source-fetch-gate.ts` judges every fetched copy against the operator's expectation (type, anchors) or the last good read. A rejected read counts as a failed fetch and the stored copy is kept. A PDF source that answers with a web page fails.
- **Hold.** `server/sourceHold.ts` leases a source to one run at a time, across instances. A second run is refused with `SourceHeldError`.
- **Source role.** Each of an agency's sources has a `source_role` (`shared/source-role.ts`). A `standards` source is read by the agency's parser and compared with the catalog. A `guidance` source is fetched, gated, stored and watched for change, but never read as requirements.
- **Change cause.** A staged difference records whose change it is (`change_cause`): the agency's only where its source changed after the row was last verified, otherwise a corrected reading. Approval keeps it on the catalog row (`last_change_cause`), and each college's delivery History row says it.

### eCFR sources

An agency source whose address names an eCFR part or less is read through the eCFR API, never as the web page (which redirects automated readers to a block page). `server/modules/rule-page-check/agency-source.ts` hands the source monitor the part's text, one line per block, or a 304 while the part's eCFR version has not moved. The version is kept in `agency_standard_sources.etag` as `ecfr-api:<version>`. A wider address stays on the ordinary fetch.

`server/parsers/ecfr.ts` reads that text into sections: the section is the requirement, and its numbered paragraphs (`99.7(a)(2)(iii)`) are its parts. The compare reads a section's own words through `ParsedStandard.statement`, and a statement too long to stage is left unread whole, never cut. The parser is registered for no agency yet; regulators keep their existing path until it is.

### Requirement parts

The numbered paragraphs a source prints inside one requirement are kept under its catalog row in `catalog_requirement_parts`, staged as `proposed_parts` on `catalog_staging_entries`. A part is never a catalog row and weighs nothing in a score. The Review Desk draws a section with parts as its outline.

### Run controls

An operator can stop or pause a live run (`RUN_CONTROLS`), resume it, re-run from the read, retry failed colleges, or choose colleges for a delivery. The routes sit under `/api/admin/pipeline-runs/:runId/*`. The run checks its `control` column between sources and stages.

## Delivery

Every sync to colleges, whichever door started it, goes through `executeSyncWithAudit` (`server/catalogSyncService.ts`) and opens a `delivery` run with one `deliver` step per college. Colleges are processed by name and standards in catalog order (`shared/delivery-order.ts`). Each delivery writes a `catalog_delivered` row on the college's own standard History.

### Renumbering

When an agency renumbers, each old catalog number gets one line in `standard_renumberings`: a successor, or none. `shared/renumbering.ts` suggests a successor only where the old requirement's words plainly sit in one new requirement; it never calls a model. Every other line waits on an operator's choice, and *Confirm the crosswalk* (`POST /api/admin/agencies/:agencyId/renumbering/confirm`) is off until every line has one. Only confirmed lines move work.

On delivery, `server/standardMove.ts` moves everything a college holds on the old number (requirements, policy, course and program links, gaps however they name the standard, evidence asks, tasks, narrative sections, walks) to the successor, keeping dates, owners and status, and writes one `standard_moved` History row. A content pack's rule follows a confirmed crosswalk line to its successor row (`server/packCatalogRow.ts`); the pack itself is not rewritten.

A standard retired with no successor stays live at a college that holds work on it, marked `standards.retired_by_agency_at` (`server/standardRetired.ts`). The college can *Move to…* another standard or *Close the work*, each with its History row. The delivery step counts what it retired (`pipeline_run_steps.standards_retired`).

The delivery's page is `/admin/runs/:id`. Its CSV, Excel, and PDF export uses the shared report foundation.

## College copies

A college holds its own copy of each standard of each agency it confirmed. `shared/college-copies.ts` decides a copy's standing:

- **To acknowledge**: a delivered change nobody at the college has acknowledged yet.
- **Behind**: the copy is older than the catalog's version.
- **Current**: otherwise.

| Route | Purpose |
| --- | --- |
| `GET /api/college/agencies` | The college's agencies and how each stands |
| `GET /api/college/copies` | The college's copies |
| `GET /api/college/deliveries` | Deliveries that reached the college |
| `POST /api/college/deliveries/acknowledge` | Acknowledge several delivered changes at once |
| `POST /api/college/agencies/:agencyId/sync` | Pull an agency that is behind (trigger `college`) |
| `GET /api/standards/:id/copy`, `POST /api/standards/:id/acknowledge` | One standard's copy and its acknowledgement |

A college member can report a requirement that looks wrong (`POST /api/college/requirements/:catalogEntryId/report`). The report is stored and read by the nightly requirement checks, never sent to an operator at the click.

The college's standards routes answer a college member from its copies, through `overlayCollegeCopies`. Confirming an agency delivers its standards at once (trigger `confirmed`). Institutional admins and compliance officers read the Manage Compliance page (`/manage-compliance`); the agency page reads the college's copies for them.

### Federal statutes

A college's federal statutes follow its Institutional Profile: Title IV participation and its control type (`shared/statute-applies.ts`). `reconcileCollegeStatutes` holds a statute that applies, switches back on one that applies again (keeping its progress and owner), and switches off one that no longer applies, never deleting it. It runs at setup's sync, on every profile save that changes either fact, and wherever statute deadlines are read, so a statute added to the platform catalog reaches colleges already set up. Each change is a History row. `GET /api/college/statutes` and `/preview` serve Manage Compliance's *Federal statutes* leaf and the profile's preview before a save.

A statute that does not apply to a college goes through the compliance exception path (a statute exception moves no points and needs an end day). While it stands the statute is off the Compliance calendar and the score; when it lapses the college's statutes are reconciled again.

## Requirement checks

A person checks catalog requirements against their source, a few each night, in an order set by one versioned rule. The requirement is what is checked; the standard is its source.

- **The rule.** `shared/requirement-checks.ts` weighs named signals, each a strength from 0 to 1: a college flag, an edition recorded, a project opened, work tied, a date within six months, how many colleges hold it, a recent failed check on its agency, the catalog's own staleness, and never verified. The rule is stored in `requirement_check_rules` and changed only by a person with a reason. A random share (5%, at least two) is drawn from what the rule passed over, to measure what the signals miss.
- **The nightly job.** `server/requirementCheckJob.ts` runs at 04:30 UTC (`REQUIREMENT_CHECKS_CRON`), after the source sweep, as a `pipeline_runs` row of job `requirement_checks`. It has no in-process fallback. It is the fourth platform clock on the desk.
- **Recording a check.** An outcome is `right`, `wrong_words`, `wrong_number` or `missing`, and a wrong one names its cause (`reading_corrected` or `agency_changed`). A right reading marks the catalog row `verified`; a wrong one `unverified`. Open college flags on the row are answered and their reporters told.
- **Held like an approval step.** Whoever opens a check holds it for 24 hours (`requirement_check_claims`). They can delegate it to another operator. Two hours before it is due they are reminded; past due it escalates to every operator, and any of them may take it. The reminder and escalation sweep runs with the five-minute approval sweep. Each act is a History row.
- **Routes.** `/api/admin/requirement-checks` (list, record, run), `/entry/:catalogEntryId` (the check's view, hold, open, snooze, delegate, take), `/learning` and `/learning/replay`, and `/api/admin/requirement-check-rule`.

### Sampled batch approval

A sync's batch on the Review Desk can be approved by sample (`server/catalogBatchSample.ts`, `catalog_batch_samples`). Removals, structure changes, figures and anything that is not a requirement's words are always shown and decided one at a time. A sample of the rest is drawn across the source's sections at a size the agency's last samples earned. A sampled proposal checked right is approved by that check. One checked wrong fails the sample: the rest go back to one at a time, and the agency's next sample is the whole batch. When every sampled proposal is right, the rest are approved in one act.

### A proposal's reach

Each staged proposal on the Review Desk says how far it reaches (`GET /api/admin/catalog-staging/reach`): the colleges holding a copy of the requirement and how many have open work tied to it, or, for a new requirement, the colleges it reaches once approved. Colleges holding their own threshold on a requirement are named, so a moving figure can be held up with them.

### Two readings

Beside the parser's structure reading, `server/modules/catalog-source-check/meaning-reading.ts` has a model, never shown the parser's reading, list every obligation a source places on an institution as the agency's own words; code holds every quote to the copy word for word. `compare-readings.ts` lays the two readings side by side, item by item, in the Review Desk's words (`new`, `updated`, `removed`, `structure_change`). Both are measured against hand-labelled reference sets (`__fixtures__/reference/`, `reference-score.ts`, `meaning-score.ts`, `scripts/meaning-reading-score.ts`). Neither writes to the catalog or is part of a Sync yet.

## The operator desk

Operators work the pipeline from `/admin/sync-station`, `/admin/catalog`, `/admin/catalog/review`, `/admin/source-monitoring`, and `/admin/parsers`.

- **Clocks.** `GET /api/admin/platform-clocks` lists the platform's clocks (`source_sweep`, `catalog_backfill`, `parse_queue`, `requirement_checks`). Run now, Pause, and Resume each write a History row.
- **Source repair.** When a source breaks, `server/sourceRepair.ts` reads candidate addresses through the fetch gate and proposes one. An operator approves it with Use this address, or snoozes it.
- **Reports.** Seven operator-only reports open at `/admin/reports/:id`: `pipeline-runs`, `source-health`, `catalog-provenance`, `review-queue`, `upgrade-interest`, `index-both-ways`, and `check-learning` (the Requirement scorecard: each signal's hit rate over recorded checks, the random share's, and a proposed rule replayed beside the one in force). Operators can save, share, and schedule them like college reports.
