Proof uses WorkOS to power single sign-on (SSO). Your identity provider (IdP) speaks SAML 2.0 or OIDC to WorkOS, and WorkOS handles the protocol details on behalf of Proof. You enter your IdP details in the WorkOS Admin Portal, so you never upload certificates or client secrets into Proof.

Every new connection is WorkOS-backed. Proof's earlier in-house OIDC and SAML connections are retired: they can no longer be created, and sign-in through them is refused.

## Who can configure SSO

The **Single Sign-On** panel is on the Proof operator console today, on the institution's (or firm's) **SSO** tab. Set up a connection with your Proof operator; there is no SSO screen in your own **Settings**.

The SSO admin API accepts these tenant administrators as well as operators:

- **Institutions**: an `institutional_admin` who is a member of the institution.
- **Firms**: an active firm owner or firm admin.

## How users sign in with SSO

When a user arrives at the Proof sign-in page, they enter their **Work email**. Proof looks up the email domain in the list of verified SSO domains.

<Steps>
  <Step title="Email lookup">
    The user types their email and Proof checks whether the domain is verified on an **active** SSO connection.
  </Step>
  <Step title="Redirect to IdP">
    If a verified domain matches, Proof redirects the user to the IdP through WorkOS. The user authenticates with their organization credentials.
  </Step>
  <Step title="Return to Proof">
    After successful authentication, the user is returned to Proof and signed in. If they are new, Proof provisions them automatically (see [JIT provisioning](#just-in-time-provisioning)).
  </Step>
</Steps>

If the domain does not match a verified domain on an active connection, the user continues with the standard sign-in flow.

## Domain ownership and verification

Before an SSO connection can go live, you must prove ownership of the email domains you want to use. Proof verifies ownership through a DNS TXT record.

- You add a TXT record at either `your-domain.com` or `_bksmrt-sso.your-domain.com`.
- The record value is `bksmrt-sso-verify=<token>`, where the token is generated by Proof.
- The token may sit inside a longer TXT value, so you can append it to an existing record.
- Once Proof sees the record, the domain status changes to **verified**.
- Only one connection can own a verified domain at a time.

Public mailbox domains, such as `gmail.com`, `outlook.com`, `yahoo.com`, `icloud.com`, and `proton.me`, cannot be claimed.

## Just-in-time provisioning

When a user signs in via SSO for the first time, Proof provisions them automatically if their account does not already exist. The account's role comes from the connection's role mapping rules, or its default role when no rule matches.

For institution connections, the user is added to the institution's members. For firm connections, the user is added to the firm as an active consultant. See [SSO roles and sessions](/sso/roles-and-sessions) for how roles are chosen and when sign-in is refused.

## Connection lifecycle

A connection moves through three statuses:

| Status | Meaning |
| --- | --- |
| **draft** | The connection was created but is not yet active. You can edit domains, role rules, and settings. |
| **active** | The connection is live. Users on verified domains will be redirected to the IdP. |
| **disabled** | The connection is inactive. All active sessions tied to it are revoked immediately. |

A connection can be activated only once it has at least one verified domain. Each tenant can have at most one active connection at a time. You can stage a replacement connection in draft while the current one remains active.

## Require SSO

When a connection is created with **Require SSO for users on matched domains (block fallback login)** and is active, users whose email domains match its verified domains must sign in through SSO. Proof refuses the standard sign-in for them with "Your organization requires single sign-on for `<domain>`." Proof operators are exempt.

## Session and security notes

- SSO sessions are stored alongside standard sessions. **Force logout all** signs out every SSO session for the tenant.
- Disabling or deleting a connection revokes all active sessions tied to that connection immediately.
- SSO sign-ins, refused sign-ins, domain changes, connection changes, and directory sync events are recorded in the SSO audit log.
- Connections show a **last used** timestamp so you can identify stale connections before disabling them.
