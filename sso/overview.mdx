Proof uses WorkOS to power single sign-on (SSO). Your identity provider (IdP) speaks SAML 2.0 or OIDC to WorkOS, and WorkOS handles the protocol details on behalf of Proof. This means you do not need to upload certificates or client secrets directly into Proof.

## Who can configure SSO

SSO is configured by tenant administrators from the Proof admin UI.

- **Institutions**: an `institutional_admin` user who is an active member of the institution can create and manage SSO connections.
- **Firms**: an active firm owner or firm admin can create and manage SSO connections.

## How users sign in with SSO

When a user arrives at the Proof sign-in page, they enter their email address. Proof looks up the email domain in the list of verified SSO domains.

<Steps>
  <Step title="Email lookup">
    The user types their email and Proof checks whether the domain is attached to an active SSO connection.
  </Step>
  <Step title="Redirect to IdP">
    If a verified domain matches, Proof redirects the user to the IdP through WorkOS. The user authenticates with their organization credentials.
  </Step>
  <Step title="Return to Proof">
    After successful authentication, the user is returned to Proof and signed in. If they are new, Proof provisions them automatically (see [JIT provisioning](#just-in-time-provisioning)).
  </Step>
</Steps>

If the domain does not match any verified SSO domain, the user continues with the standard sign-in flow.

## Domain ownership and verification

Before an SSO connection can go live, you must prove ownership of the email domains you want to use. Proof verifies ownership through a DNS TXT record.

- You add a TXT record at either `your-domain.com` or `_bksmrt-sso.your-domain.com`.
- The record value is `bksmrt-sso-verify=<token>`, where the token is generated by Proof.
- Once Proof sees the record, the domain status changes to **verified**.
- Only one connection can own a verified domain at a time.

Public mailbox domains, such as `gmail.com`, `outlook.com`, and `yahoo.com`, cannot be claimed.

## Just-in-time provisioning

When a user signs in via SSO for the first time, Proof provisions them automatically if their account does not already exist. The user's role is determined by role mapping rules or the connection's default role.

For institution connections, the user is added to the institution's membership list with the role `member`. For firm connections, the user is added as an active consultant.

## Connection lifecycle

A connection moves through three statuses:

| Status | Meaning |
| --- | --- |
| **draft** | The connection was created but is not yet active. You can edit domains, role rules, and settings. |
| **active** | The connection is live. Users on verified domains will be redirected to the IdP. |
| **disabled** | The connection is inactive. All active sessions tied to it are revoked immediately. |

Each tenant can have at most one active connection at a time. You can stage a replacement connection in draft while the current one remains active.

## Require SSO

When you enable **Require SSO for users on matched domains**, users whose email domains match the connection's verified domains must sign in through SSO. The standard fallback sign-in is blocked for those users.

## Session and security notes

- SSO sessions are stored alongside standard sessions. Admins can force logout all SSO sessions for a tenant.
- Disabling or deleting a connection revokes all active sessions tied to that connection immediately.
- Every SSO sign-in, failure, and administrative change is recorded in the SSO audit log.
- Connections show a **last used** timestamp so you can identify stale connections before disabling them.
