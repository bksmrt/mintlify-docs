SIS writeback sends approved catalog changes from Proof into an SIS, so a revised course or program does not have to be re-entered by hand.

<Warning>
  Writeback runs only on vendor API connections (Ellucian Banner, Colleague, and Workday), and a college cannot connect those today. The SFTP / CSV Drop, the feed a college can connect, reads files and never writes back. If your college uses the CSV feed, update your SIS from the approved changes in Proof yourself.
</Warning>

The rest of this page describes how writeback behaves on a vendor connection where it is turned on.

## What writeback does

Writeback updates existing SIS records only. It never creates or deletes records in the SIS. When a project that changed the catalog is approved, Proof queues a writeback job for each of the institution's connections that have writeback turned on. These record types can be sent:

| Record type | Fields sent |
| --- | --- |
| **Course** | Title, subject, course number, description, short description, credits, contact, lecture, lab and clinical hours, CIP code, fund code |
| **Program** | Name, code, description, total credits, expected terms, CIP code |
| **Prerequisite** | Link type, whether it is required, minimum grade, notes |
| **Requirement group** | Name, description, requirement type, required credits, minimum and maximum courses, sequence order, recommended term |

A record with no SIS key (one that did not come from the SIS) is not sent.

## Settings on a connection

Each connection has its own writeback settings, changed only by an institutional admin or a compliance officer granted SIS management:

- **Master switch**: off by default. While off, the connection gets no writeback jobs.
- **Writable record types**: none by default. Each type must be allowed explicitly.
- **Schedule**: when queued jobs run: every 15 minutes (the default), hourly, daily, weekly, or off. When off, jobs wait until someone chooses **Run now** from the job's menu on the **Write-back jobs** page.

## Safety

- **One job at a time**: only one writeback job per connection runs at once.
- **Optimistic concurrency**: each write carries the last SIS value Proof read, as `If-Match` where the vendor supports it. If the SIS record changed since then, the write is refused as a conflict instead of overwriting newer data.
- **Idempotency**: every row carries a stable correlation ID, so approving the same project again does not queue the same writes twice.
- **Deadline**: a job stops after 10 minutes.

## Writeback outcomes

Each row in a writeback job receives one of the following outcomes:

| Outcome | Meaning |
| --- | --- |
| **Applied** | The SIS accepted the write and updated the record |
| **Skipped** | The record was unchanged or not eligible for writeback |
| **Conflict** | The SIS refused the write because the record changed there since the last read (HTTP 409 or 412) |
| **Failed** | The SIS returned an error (for example, 400, 404, or 5xx) or the request failed |

An HTTP 401 or 403 pauses the connection: its status becomes authentication failing, and writeback stops until an institutional admin rotates the credentials and clears the pause.

## Rate limits and backoff

If the SIS returns rate-limit responses (HTTP 429) or transient server errors, the writeback engine backs off per connection. The wait doubles after each consecutive failure, up to 60 seconds.

## Conflicts and jobs

When a writeback row returns a conflict, it appears on the **Write-back conflicts** page, together with rows the SIS failed to take. An institutional admin, or a compliance officer with the SIS management grant, chooses **Resolve…** from the row's menu. The **Resolve write-back conflict** dialog shows **Catalog (proposed)**, **SIS (last known baseline)**, and **SIS (observed now)** side by side, then offers three choices:

- **Local wins — apply catalog → SIS**: push the Proof value to the SIS
- **Remote wins — pull SIS → catalog**: keep the SIS value and update Proof to match
- **Merge — push a hand-curated value to SIS**: pick a side per field with **Use catalog** or **Use SIS**, or edit the value directly

Every resolution needs a written reason of at least 15 characters. Under **Filters**, narrow the conflicts by **Connection** and **Type** (course, program, department, prerequisite, or requirement group), or search external keys and reasons.

The **Write-back jobs** page lists each job with its trigger (project approval, manual, scheduled, or retry), its times, and its counts of applied, skipped, conflict, and failed rows. Under **Filters**, narrow the list by **Status** and **Connection**; you can pick several values in each, for example both **Failed** and **Partial**. Each job's menu offers **Details**, a queued job also offers **Run now**, and a failed or partial job **Retry**. Inside a job's details, each failed or pending row has its own **Retry** and **Skip** buttons; a skip asks for a reason.

## Turning writeback off

If you turn writeback off or disconnect the integration, queued jobs stay queued but do not run. Nothing is deleted on the SIS side.
