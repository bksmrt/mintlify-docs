When your SIS feed runs, Proof's engine reads the files, applies your column mappings, writes the changes to your catalog, and records each outcome in a run report. Understanding this pipeline helps you read run results, fix mapping problems, and decide when to intervene.

## Field mapping

Before any record is written, the engine copies each column to the Proof field you mapped it to. You set this on the **Columns** step when you connect the feed, and change it later in the **Columns** panel of the **Student records** section with **Save columns**.

### Default mappings

The CSV feed maps each field to a column of the same name in its file, for example `course_number` to the course number. See [File names and CSV columns](/sis/sftp-csv#file-names-and-csv-columns) for every default. If your CSV uses different column names, pick the right **Column** for each field.

### Transforms

Each field can apply one transform, shown as **Tidy it**:

| Transform | Effect | Example |
| --- | --- | --- |
| `uppercase` | Converts the value to uppercase | `bio` becomes `BIO` |
| `trim` | Removes leading and trailing whitespace | `" ENG "` becomes `ENG` |
| `to_int` | Parses a number and drops any decimals | `"3"` becomes `3` |
| `to_float` | Parses a number | `"3.5"` becomes `3.5` |
| `to_iso_date` | Parses a date and writes it as an ISO 8601 timestamp in UTC | `2026-08-24` becomes `2026-08-24T00:00:00.000Z` |

A value a transform cannot read (for example, `three` under `to_int`) is left out, and the run records a warning on that record. The column preview applies the same transforms, so it shows what the run will write.

### Required fields

Each record type has its own required fields: a course needs a subject, course number, and title; a program needs a name and credential type; a department a name; a term a code and name; a faculty member a full name. A row missing one is refused, and the run report gives the reason.

## The sync run engine

A sync run proceeds through the following stages:

<Steps>
  <Step title="Lock and read">
    The engine takes a lock per connection and module, so two runs of the same module cannot overlap. It then reads the files from the SFTP folder.
  </Step>
  <Step title="Apply mappings">
    Each row is transformed using the feed's column mappings and transforms.
  </Step>
  <Step title="Write in batches">
    Mapped records are written in batches of 500. Departments are written before courses, so a course can find the department its code names. For each row, the engine creates a record, updates one, skips it, or refuses it.
  </Step>
  <Step title="Archive missing records">
    After a run that writes and has no failures, rows of each record type that came from this feed but are missing from that type's file are archived. A file that is missing or empty archives nothing for its type, so an emptied export never wipes your catalog. A preview never archives.
  </Step>
  <Step title="Record outcomes">
    Each batch updates the run's counts and keeps a record of what happened to each row, by name and with its reason.
  </Step>
</Steps>

## Run triggers

| Trigger | How to start | Behavior |
| --- | --- | --- |
| Manual | Click **Sync now** in the **Student records** section | Runs the feed's enabled modules and writes to the catalog |
| Preview | Click **Preview** in the **Student records** section | Reads the files and shows what would happen, without writing |
| Scheduled | Pick a schedule under **Runs** (click **Change**) | Runs automatically at the chosen cadence |

Testing the folder while you connect is not a run. It only signs in and lists the files.

## Scheduling options

Under **Runs**, choose **Nightly, around 2:00**, **Weekly, around 2:00**, or **Only when someone presses Sync now**. Proof spreads scheduled runs by up to ten minutes either side of 2:00, which is why the section says *around*. A weekly run repeats every seven days from when you set it.

Scheduled runs dispatch only while the feed is live. A paused feed, or one whose stamp reads **Failing** because it could not sign in, does not run on schedule until you click **Resume** or update the password.

## Changes made in Proof

When a synced record differs from the incoming row, the engine compares the fields the file carries and updates only those. These cases leave the record as it is and skip the row:

- The college marked the record as a manual override, so the SIS no longer owns it.
- The college archived the record by hand. The sync leaves it archived.
- Nothing changed.

Fields the file does not carry are never cleared, and server-owned fields such as the catalog year are never overwritten. Courses are written into the active catalog year.

## Run statuses

The **Runs** list stamps each run with what happened:

| Stamp | Meaning |
| --- | --- |
| **Running** | Queued or in progress |
| **Preview** | A preview finished; nothing was written |
| **Filed** | Every row was written or skipped |
| **Filed · some wait** | The run finished, but some rows were refused and wait on you |
| **Filed · a part failed** or **Preview · a part failed** | One module failed and another finished |
| **Failed** | The run failed, for example because the folder could not be read |
| **Could not sign in** | The run failed because the SFTP sign-in was refused |

Underneath, a run's status is `queued`, `running`, `completed`, `partial`, `failed`, `stalled` (the process stopped mid-run), or `cancelled`.

## Reading a run

Open a run in the **Runs** list to see its report:

- **Waits on you · worst first** (**Would wait on you** for a preview): each refused row by name, with the reason and where to fix it. A course whose department has no administrative unit comes first, since it holds back every course filed under that department.
- **Filed** (**Would be filed** for a preview): each written row by name, with what happened, such as the department a course was filed under.

If many rows wait on you, check the column mappings first. Most refusals come from missing required columns, mismatched department codes, or column names that changed in the export.

## Webhook events

When a sync run finishes, Proof emits a webhook event you can consume:

- `sync.run.finished` when the run ends `completed` or `partial`
- `sync.run.failed` when the run ends `failed`

Previews send these events too, with `isDryRun: true`. The payload includes the run ID, connection ID, modules, and final status. To learn how to receive and verify these events, see the [webhooks overview](/webhooks/overview) and [webhook events](/webhooks/events).
